# PR : feat(llm+ui): active waiting during real LLM calls (P75, issue #181)

- Date : 2026-11-21
- Branche : feat/181-p75-llm-activity
- Issue : #181

## Livré

- **Couche LLM** : `CallState` (usage, model, started_at, ended_at, error,
  `in_progress`) exposé par `LLMProvider.call_states()` ; le mock
  instantané n'enregistre que des appels terminés, `MistralProvider`
  enregistre début/fin/erreur autour de chaque appel (repli narration
  compris).
- **API** : `GET /v1/llm/calls` (401/503 comme `/v1/llm/usage`),
  contrat documenté dans `openapi.yaml`.
- **UI** : `useLlmActivity` (poll 1 s pendant la requête) + composant
  `<LlmBusy>` branché sur les trois étapes concernées par un appel LLM
  (profil sémantique à l'amorçage, grille de lecture aux questions,
  narration du témoin aux vérifications) : sablier animé + libellé de
  l'usage en cours traduit + durée écoulée dans `role="status"`.
  Chaînes fr/en complètes (`llm.*`, `amorcage.loadingProfile`).
- **Tests** : provider à latence simulée (état « en cours » visible pendant
  l'appel, erreur enregistrée), endpoint 200/401/503, composant avec
  latence simulée (succès après attente, erreur après délai, libellés
  fr/en).

## Décision consignée (point « À VÉRIFIER » de l'issue)

Streaming vs `response_format: json_schema` : avec un schéma strict, les
tokens streamés sont le document JSON lui-même (pas un canal de réflexion
séparé) — le texte de réflexion en progressif n'a pas de sens ici. Décision :
**pas de streaming de texte de réflexion** ; sablier + usage + durée
écoulée suffisent ; le JSON final reste toujours archivé complet (P72).
