# PR : fix(auth): fall back to legacy X-API-Key when AUTH_ISSUER is unset (502 on petrichor.linard.fr)

- Date : 2026-11-21
- Branche : fix/202-auth-env-fallback
- Type : hotfix (production down)

## Diagnostic

- `petrichor.linard.fr` → 502 depuis le deploy de PR #202 ; deploys des
  PR #202 et #203 en échec (run 44879944401, 44884270075), conteneur
  `api` « unhealthy ».
- Cause racine : depuis PT-2, `main()` → `build_token_verifier()` exige
  `AUTH_ISSUER` (champ requis, PT-1) ; `docker-compose.yml` ne forwardait
  que `PETRICHOR_API_KEY` → `ValidationError` au démarrage → conteneur
  down → nginx 502. Reproduit localement.
- Côté IdP vérifié en direct : `https://auth.linard.fr/.well-known/
  openid-configuration` répond (`issuer=https://auth.linard.fr`,
  `jwks_uri=https://auth.linard.fr/oauth/v2/keys`) — Zitadel est bon.

## Correctif

- `main.py` : `build_token_verifier` retourne `None` + warning structuré
  `auth_bearer_not_configured` quand `AUTH_ISSUER` est absent/vide.
  L'API reste protégée par le `X-API-Key` obligatoire sur `/v1/` (jamais
  ouverte) ; avec `AUTH_ISSUER` renseigné, le verifier PT-1 est câblé
  comme avant, garde-fou L3 inchangé.
- `docker-compose.yml` : forward de `AUTH_ISSUER`, `AUTH_CLIENT_ID`,
  `AUTH_CLIENT_SECRET`, `AUTH_ALLOWED_AUDIENCES`, `AUTH_DISABLED`,
  `PETRICHOR_ENV` depuis le `.env` hôte vers le conteneur.
- `deploy/deploy.sh` : message indiquant si la couche Bearer sera active.
- `deploy/README.md` : bloc `.env` Zitadel à ajouter sur le VPS.
- Tests : +4 (fallback sans AUTH_ISSUER avec log piné, chaîne vide,
  401 sans credential en fallback, 200 avec X-API-Key en fallback).

## Limites connues

- Tant que le `.env` du VPS n'a pas `AUTH_ISSUER`/`AUTH_CLIENT_ID`/
  `AUTH_CLIENT_SECRET` (+ `PETRICHOR_ENV=production`), le site revient en
  mode X-API-Key seul ; le Bearer s'active au prochain deploy après ajout.
