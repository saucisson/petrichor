# PR : feat(auth): Bearer middleware on the API with legacy X-API-Key passthrough (PT-2, issue #183)

- Date : 2026-11-21
- Branche : feat/183-pt2-api-middleware
- Issue : #183

## Livré

- `src/petrichor/api/auth.py` (nouveau) : `authenticate_request` — un
  `Authorization: Bearer <JWT>` valide (brique PT-1 `TokenVerifier`) ou
  l'ancien `X-API-Key` (comparaison temps constant) passent par le même
  middleware. Claims validés exposés aux handlers via
  `environ["petrichor.auth_claims"]` + `auth_claims_from_environ`.
  `AUTH_DISABLED=1` = bypass L3 (décision `AuthDecision` gelée).
- `app.py` : porte d'auth extraite en `_auth_gate` (C901 : `create_app`
  reste ≤ 10). Refus = 401 problem uniforme (`invalid_bearer_token` si un
  header Authorization a été rejeté, sinon `missing_or_invalid_api_key`)
  + log `api_request_unauthorized` avec la raison exacte (jamais dans le
  corps). Tests 401 existants inchangés et verts.
- `main.py` : `build_token_verifier` câble `AuthSettings` +
  `TokenVerifier` depuis l'environnement (aucun I/O au démarrage).
  Garde-fou L3 : `AUTH_DISABLED=1` + `PETRICHOR_ENV=production` →
  `ConfigurationError` fatale (testé, conforme au niveau L3 du cadrage).
- `openapi.yaml` : réponse `Unauthorized` documente les deux credentials
  (ADR-0016).
- `tests/test_api_auth.py` (nouveau) : 13 tests — 401 / acceptation via
  verifier stubbé (aucun réseau), pin du log avec raison exacte,
  exposition des claims, bypass L3, garde-fou production. Deux tests
  `main()` existants reçoivent `AUTH_ISSUER`/`AUTH_CLIENT_ID` en env
  (config désormais requise ; assertions inchangées).
