# ADR-0018: React + TypeScript frontend under the same discipline

- Status: accepted
- Date: 2026-11-03

## Context

The template targets full-stack products: a Python backend and a web
frontend. For agents to work autonomously on the frontend, the same
two guarantees the Python side provides are needed mechanically:
a **layer contract** (import-linter's onion) and a **strict, unarguable
checker** (mypy strict). A locally-run dev server is not a gate; the
template also needs one shared runtime to prove the pieces build and
run together.

## Options considered

1. **JavaScript or loosened TypeScript.** Rejected: without a
   strict compiler, the reviewer agent cannot trust "it type-checks"
   evidence, and agents drift toward `any` under pressure.
2. **A full framework (Next.js or similar).** Rejected: routing,
   SSR and server conventions smuggle in architecture decisions the
   template wants to leave to the product; the lock-in narrows where
   the template applies.
3. **Vite + React + strict TypeScript with enforced layering.**
   Chosen: minimal, mainstream tooling; every guarantee is a config
   file the reviewer can read; the layering mirrors the Python onion
   so one mental model covers both sides.
4. **docker compose as the shared runtime.** Chosen alongside: one
   command builds and starts the web app and the notify tool together;
   production deployment stays the owner's business.

## Decision

- The frontend lives in **`apps/web/`**: Vite + React + TypeScript,
  Node 24, `package.json` scripts as the only entry points
  (`make web-*` wraps them).
- **Layer contract, enforced by `eslint-plugin-boundaries`** (the
  import-linter equivalent):
  `app` (composition root) → `components` (presentation) →
  `hooks` (React primitives) → `lib` (pure logic). Dependencies point
  inward only; `lib` imports nothing internal.
- **Strict-plus `tsc`**: `strict` plus `noUncheckedIndexedAccess`,
  `exactOptionalPropertyTypes`, `noUnusedLocals`,
  `noUnusedParameters`, `noImplicitOverride`,
  `verbatimModuleSyntax`. Plus **type-checked eslint**
  (typescript-eslint `recommendedTypeChecked`).
- **Style parity with the Python rules (ADR-0004/0006)**, enforced by
  eslint: no `any` (use `unknown` and narrow), closed sets as **union
  types, never enums** (banned), exhaustive `switch` with a `never`
  guard, named exports only, sorted imports, no `console`, `UPPER_CASE`
  constants, kebab-case files.
- **Testing parity**: vitest + Testing Library, 90 % coverage
  thresholds on lines, branches, functions and statements - the same
  floor as pytest. Tests colocate with sources
  (`src/**/*.test.tsx`).
- **Gate parity**: a `web` CI job on GitHub and a `web-quality-gate`
  job on GitLab; `make check` runs both the Python and web gates;
  a pre-commit eslint hook fires only when web files changed.
- **docker compose** wires the two images (`notify`, `web`) as the
  shared local runtime; each image is multi-stage with a non-serving
  build stage.

## Consequences

- Two toolchains to maintain - accepted: Renovate owns dependency
  bumps for both (ADR-0015), and both lockfiles are committed at
  setup like `uv.lock`.
- `npm ci` needs `package-lock.json`, generated by the setup step
  (`make web-install`); until then the web gate is red - same honest
  state as Python before `uv sync`.
- Agents working on web code must run `make web-check` before
  reporting; the reviewer bundle already includes
  `docs/architecture.md` and the review checklist, so the TypeScript
  rules reach the reviewer with no extra wiring.
- Version pins in `package.json` are ranges resolved by setup;
  Renovate keeps them current afterwards.
- `main.tsx` is excluded from coverage thresholds: it is mount
  boilerplate, proven by `docker compose build` and the preview.
